SUMMARY
========================================================================

Severity counts:
  Critical   6
  High       6
  Medium    ~14
  Low       ~20

The security fundamentals are genuinely strong: no XSS sinks, no SQL injection,
JWT fails closed with no default secret, algorithm pinned, role read from the
database rather than trusted from the token, every admin route properly
role-gated, and no secrets or database files ever committed to git.

The real problems are concentrated in three places:
  1. Validation ordering — input rules enforced on the *response* model instead
     of the request model, so bad data is committed and the request then fails.
  2. Destructive operations whose blast radius is not visible at the call site.
  3. Assorted correctness bugs in async React code and in timezone handling.

Strongest quick wins (small diff, large risk reduction): items 2, 3, 5, 7, 12.

1. PRODUCT PRICE VALIDATION RUNS AFTER THE DB WRITE
   backend/schemas.py:118, backend/schemas.py:129, backend/app.py:803

   ProductCreate and ProductUpdate enforce only `ge=0`. The real rule
   (old_price >= new_price, and expiration_date >= creation_date) lives solely
   on the RESPONSE model:

       @model_validator(mode="after")
       def _check_product_constraints(self) -> "ProductResponse":
           if self.old_price < self.new_price:
               raise ValueError("old_price must be greater than or equal to new_price")

   That validator is evaluated at:

       product = Product(**body.model_dump(exclude={"image_url"}))
       db.add(product)
       await db.flush()
       await _apply_image(...)
       await db.commit()                          # <-- row is already written
       return ProductResponse.model_validate(product)   # <-- raises -> 500

   Any authenticated worker can POST old_price=1, new_price=99. The row is
   committed, then model_validate raises pydantic.ValidationError, which is not
   caught -> unhandled 500. The bad data persists.

   This also poisons reads. ProductMinimalResponse (schemas.py:223-227) carries
   the same validator, so a single legacy bad row makes GET /products/{store_id}
   return 500 for every future request for that store.

   FIX: move the price/date constraints into a shared validator applied by
   ProductCreate and ProductUpdate, so invalid input returns 422 and never
   reaches the database.

2. DELETE /stores SILENTLY DISABLES ALL PRODUCTS AND ALL WORKER ACCOUNTS
   admin/app.py:320 -> backend/app.py:675-703

   The admin panel presents this as harmless:

       if st.button("Delete store (soft)", key=f"{prefix}_delete"):
           try:
               backend.delete_store(store["id"])
               st.success("Store deleted.")
               st.rerun()

   The endpoint is actually a cascade:

       @app.delete("/stores/{store_id}", status_code=204,
                   dependencies=[Depends(require_admin)])
       async def delete_store(store_id, db) -> None:
           """DELETE /stores/{id} — soft-delete a store, along with its
           products and workers (admin only)."""
           store.is_active = False
           await _clear_image(store)
           products = ... Product.store_id == store_id, is_active is True ...
           for product in products:
               product.is_active = False
               await _clear_image(product)      # hard-deletes ImageKit files
           workers = ... User.role == worker, User.store_id == store_id ...
           for worker in workers:
               worker.is_active = False

   Blast radius of one misclick, with no confirmation prompt and the button
   placed directly beneath "Save changes":
     - the store is deactivated
     - every product is deactivated
     - every worker account is deactivated (locking out the entire staff)
     - all uploaded ImageKit files are permanently deleted, not soft-deleted

   The README (lines 111-112) documents only "Store and product deletes are
   soft deletes ... also remove any uploaded ImageKit image". It never mentions
   the product or worker cascade.

   NOTE: the cascade implementation is itself correct and defensible (disabling
   the workers of a dead store prevents orphaned access). The defect is
   entirely in the label, the missing confirmation, and the README.

   FIX: wrap in a confirmation step; relabel to
   "Delete store AND its products and workers"; report the affected counts in
   the prompt. Update README.

3. SSRF VIA THE ADMIN PANEL "BACKEND URL" FIELD
   admin/app.py:152-158, admin/api.py:37-53

       backend_url = st.text_input("Backend URL", value=st.session_state.backend_url)
       ...
       if submitted:
           try:
               data = Backend(backend_url).login(email, password)

   There is no scheme check, no host allowlist, and no DNS-resolution check.
   Anyone who can reach the panel can point it at an internal address such as
   the cloud metadata endpoint or an internal admin service, and read the
   response body back out of the UI (app.py:160, via st.error(error.detail)).

   The request is issued BEFORE the role check at app.py:162, so this is
   reachable pre-authentication. Redirects are not followed (httpx default),
   which limits chaining.

   MITIGATION: the documented run command binds to loopback
   (README.md:89, --server.address 127.0.0.1), which materially reduces
   reachability. The application itself has zero defense.

   FIX: validate before constructing the client — require https, or http only
   for localhost/127.0.0.1/::1; resolve the hostname and reject private,
   loopback, and link-local addresses (this also blocks DNS rebinding). Consider
   making the backend a dropdown of known values rather than free text.

4. SQLALCHEMY echo=True LOGS ALL SQL AND BOUND PARAMETERS
   backend/db.py:21

       engine = create_async_engine(DATABASE_URL, echo=True)

   SQLAlchemy 2.0 logs the statement AND its bound parameter values. Every
   bcrypt password hash, every user email, and every store/product row body is
   written to stdout on every request. Also a meaningful performance cost.

   FIX (one line):
       engine = create_async_engine(DATABASE_URL, echo=os.getenv("SQL_ECHO") == "1")

5. SHIPPED ENTRYPOINT BINDS 0.0.0.0 WITH THE DEV AUTORELOADER
   backend/main.py:5

       uvicorn.run("backend.app:app", host="0.0.0.0", port=8000, reload=True)

   reload=True is development-only and explicitly unsupported in production.
   0.0.0.0 exposes the API to the whole LAN. There is no [tool.uvicorn] config
   or [project.scripts] entry point in pyproject.toml, so this is literally
   what the README tells a reader to run (README.md:69).

   FIX: host=os.getenv("HOST", "127.0.0.1"), reload=bool(os.getenv("RELOAD")).
   Better: move the dev settings to a separate module.

6. NO RATE LIMITING ON LOGIN + TIMING ORACLE FOR USER ENUMERATION
   backend/app.py:538-541

       result = await db.execute(select(User).where(User.email == _normalize_email(body.email)))
       user = result.scalar_one_or_none()
       if user is None or not verify_password(body.password, user.password_hash):
           raise HTTPException(status_code=401, detail="Invalid email or password")

   Two problems:
     - For an unknown email, verify_password (bcrypt, ~100ms) is never executed,
       so the response returns measurably faster than for a known email. This is
       a user-enumeration timing oracle.
     - There is no rate limiting, lockout, or backoff anywhere in the stack.
       bcrypt gives ~100ms/attempt, which caps throughput but does nothing
       against a patient attacker.

   recover_account (app.py:614-625) has the same short-circuit shape.

   NOTE: the recovery-code endpoint already implements the correct pattern
   (RECOVERY_CODE_COOLDOWN_SECONDS at app.py:118-119). Login should mirror it.

   FIX: always run a dummy bcrypt comparison for unknown emails; add per-email
   and per-IP failure counters with exponential backoff.

9. PRODUCT SHEET DRAG LISTENERS LEAK AND CAN STICK TO THE CURSOR
   frontend/src/ProductSheet.tsx:66-92

   window.addEventListener('pointermove', move)
   window.addEventListener('pointerup', end)
   window.addEventListener('pointercancel', end)

   The three listeners are removed ONLY inside the `end` handler (:86-88).
   There is no useEffect cleanup and no setPointerCapture.

   If the pointer is released outside the window (dragged off the top edge,
   over browser chrome, or on an iOS app switch), pointerup/pointercancel never
   fire on window. The listeners live forever, and every subsequent pointermove
   on the page calls setDragHeight(next) — the sheet follows the mouse around
   the screen until reload. It also calls setState after unmount.

   FIX: register the listeners inside an effect with a cleanup, and call
   setPointerCapture in beginDrag so the pointer is captured to the element.

10. IMAGE SIZE LIMIT ENFORCED AFTER FULL BUFFERING IN MEMORY
    backend/app.py:485-493

        async def _read_valid_image(image: UploadFile) -> bytes:
            if not (image.content_type or "").startswith("image/"):
                raise HTTPException(status_code=400, detail="Uploaded file must be an image")
            data = await image.read()                 # <-- entire body in RAM
            if not data:
                raise HTTPException(status_code=400, detail="Uploaded image is empty")
            if len(data) > MAX_IMAGE_BYTES:           # <-- checked only now
                raise HTTPException(status_code=413, detail="Image too large (max 10 MB)")

    await image.read() materializes the whole upload as a single bytes object
    before the 10MB check, and no request-body limit is configured at the server
    or proxy. An authenticated worker or admin can OOM the process.

    FIX: read in bounded chunks and abort as soon as the running total exceeds
    the cap:
        data = await image.read(MAX_IMAGE_BYTES + 1)
    and consider a server/proxy body limit.

11. httpx IS IMPORTED BUT NOT DECLARED AS A DEPENDENCY
    admin/api.py:8, pyproject.toml:7-19

        import httpx

    httpx is NOT in pyproject.toml's dependency list. It resolves only because
    imagekitio and streamlit both pull it in transitively (httpx 0.28.1 in
    uv.lock). If either upstream drops it, or the admin panel is ever split
    into its own package, admin/app.py breaks with a confusing
    ModuleNotFoundError.

    FIX: add "httpx>=0.28.1" to pyproject.toml and re-run uv lock.

12. FILE ACCEPTANCE TRUSTS ONLY THE CLIENT-DECLARED content_type
    backend/app.py:486, admin/api.py:58-70

        if not (image.content_type or "").startswith("image/"):
            raise HTTPException(status_code=400, detail="Uploaded file must be an image")

    Any file type is accepted by spoofing the Content-Type header. The
    extension is separately accepted if it is 1-5 alphanumeric characters, so
    ".exe" passes. Files land on ImageKit and are served from a trusted CDN, so
    this can host arbitrary content under the app's image domain. Not code
    execution on this server.

    The admin client already has _sniff_image_type (admin/api.py:58-70) with
    real magic-byte checks, but they are only REACHED when the declared type is
    absent or non-image. In practice image.type is always present for
    st.file_uploader, so the declared type always wins — and that same declared
    value is what the backend validates. Net result: "server-side validation" of
    a fully client-controlled header.

    FIX: reorder _sniff_image_type so content sniffing always wins and the
    declared type is only a fallback; enforce a fixed extension allowlist on
    the backend too.

    .streamlit/config.toml.

    RE-VERIFITS THE TOKEN OR ROLE SERVER-SIDE

REVIEW METHOD AND LIMITS
========================================================================

Three independent deep reviews were run in parallel (backend security and
correctness; React frontend; admin panel plus tooling and git hygiene), then
every Critical and High finding was independently re-verified by reading the
quoted source directly before inclusion. eslint and tsc were actually executed
to produce the tooling-state figures above rather than estimated.

Known limits of this review:
  - The reviewers read code; they did not run the application, send live
    requests, or exercise the Leaflet map on a real device. Findings about
    runtime behavior (drag behavior, marker churn, layout on mobile) are
    derived from code analysis plus the installed react-leaflet source, not
    from observation.
  - No test suite exists, so no finding was confirmed by a reproducing test.
  - Findings #33 (haversine domain error on out-of-range coordinates) and the
    exact Streamlit selectbox fallback behavior in #14 were analyzed but not
    reproduced; both are flagged as such in their entries.
  - Performance findings (#4 in the frontend review, marker re-binding) are
    reasoned from react-leaflet's source but not measured on a device.
  - Streamlit's default maxUploadSize=200 MB and address default were confirmed
    by reading the installed streamlit/config.py, not from documentation.
